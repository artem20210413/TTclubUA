# Архітектура рантайму `.specify/`

> Переклад українською. Канонічним джерелом істини є `ARCHITECTURE.md` (англійською).

Кожен скіл `speckit-*` — це markdown-промт (`SKILL.md`), за яким слідує агент, але *стан* і
*механіка* конвеєра живуть у `.specify/`. Цей документ пояснює кожну складову.

## Конфігураційні файли

### `.specify/feature.json`

```json
{ "feature_directory": "specs/008-purchase-request-api" }
```

Єдиний вказівник на те, «над якою фічею ми зараз працюємо». Записується `create-new-feature.sh`
(викликається опосередковано через `speckit-specify`) і читається кожним іншим скілом через
`get_feature_paths()` у `common.sh`. Порядок резолюції, коли скілу потрібна активна директорія
фічі:

1. Змінна середовища `SPECIFY_FEATURE_DIRECTORY`, якщо користувач/сесія явно її встановили (і
   якщо так — вона зберігається назад у `feature.json`, щоб наступні команди в наступних сесіях
   все одно її підхопили).
2. Поле `feature_directory` у `.specify/feature.json`.
3. Інакше: жорстка помилка з проханням спочатку запустити `speckit-specify`.

Read-only викликачі (наприклад, `check-prerequisites.sh --paths-only`) передають `--no-persist`,
щоб саме лише *запитування* активної фічі ніколи не мало побічного ефекту запису в робоче
дерево.

### `.specify/init-options.json`

```json
{
  "ai": "claude",
  "ai_skills": true,
  "feature_numbering": "sequential",
  "here": true,
  "integration": "claude",
  "script": "sh",
  "speckit_version": "0.14.2.dev0"
}
```

Фіксується у момент `specify init`. Ключові поля:

- **`ai` / `integration`**: для якого агента-кодера підготовлено проєкт (`claude`, `copilot`,
  `gemini`, `opencode` тощо). Визначає, чи команди лежать як `.claude/skills/speckit-*/`,
  `.github/agents/` тощо.
- **`ai_skills`**: `true` означає, що інтеграція використовує механізм *Skills* (один
  `SKILL.md` на команду, з автовиявленням), а не плоскі markdown-файли slash-команд.
- **`feature_numbering`**: `"sequential"` → `specs/001-foo`, `002-bar`, … (3 цифри, з нулями
  зліва, обчислюється скануванням існуючих директорій `specs/`). Альтернатива —
  `"timestamp"` → `specs/20260319-143022-foo`. (Застарілий ключ `branch_numbering` все ще
  читається як fallback для старих установок, з одноряковим попередженням про застарілість.)
- **`script`**: `"sh"` означає, що Spec-Kit згенерував POSIX/bash-хелпери
  (`.specify/scripts/bash/`), а не еквіваленти на PowerShell.
- **`speckit_version`**: зафіксована версія, з якою цей проєкт було ініціалізовано/оновлено.

### `.specify/integration.json`

```json
{
  "integration_settings": {
    "claude": { "script": "sh", "invoke_separator": "-" }
  },
  "default_integration": "claude"
}
```

Повідомляє хелпер-скриптам, як *відобразити* назву команди назад користувачу.
`invoke_separator` дорівнює `"-"` для Claude Skills (тобто `speckit.git.commit` →
`/speckit-git-commit`), але `"."` для інтеграцій, що зберігають форму через крапку.
`format_speckit_command()` у `common.sh` використовує це, щоби виводити правильні підказки
викликів хуків (наприклад, у блоках хуків розширень, які видає кожен скіл).

### `.specify/memory/constitution.md`

Керівний документ проєкту — див. розділ «Що є унікальним саме для цього проєкту» у README.md
щодо реальних двох принципів *цього* репозиторію. Структурно: HTML-коментар
**Sync Impact Report** на початку (зміна версії, які шаблони перевірено на узгодженість,
відкладені TODO), далі `## Core Principles` (по одній підсекції `###` на принцип, кожна з
обґрунтуванням), потім `## Governance` (процедура внесення змін, правило версіонування,
очікування щодо перевірки відповідності). Версіонується за semver: MAJOR = принцип видалено/
перевизначено несумісно, MINOR = принцип додано, PATCH = лише формулювання. Лише
`speckit-constitution` має право писати у цей файл.

## Спільні shell-хелпери (`.specify/scripts/bash/`)

Усі скіли звертаються до них замість дублювання логіки шляхів/JSON інлайн.

### `common.sh`

Спільна бібліотека, яку підключає («source») кожен інший скрипт. Помітні функції:

- **`get_repo_root()`** — йде вгору від `pwd`, шукаючи директорію `.specify/` (маркер проєкту),
  щоб Spec-Kit завжди резолвився до кореня *цього* проєкту, навіть якщо викликаний із вкладеного
  пакету в монорепо. Враховує перевизначення `SPECIFY_INIT_DIR` для CI/неінтерактивного
  використання.
- **`get_feature_paths()`** — єдине джерело істини для кожного шляху, потрібного скілу:
  `REPO_ROOT`, `CURRENT_BRANCH`, `FEATURE_DIR`, `FEATURE_SPEC`, `IMPL_PLAN`, `TASKS`,
  `RESEARCH`, `DATA_MODEL`, `QUICKSTART`, `CONTRACTS_DIR` — усе видається як рядки `KEY=value`,
  призначені для `eval` викликачем, зі значеннями, безпечно екранованими через `printf '%q'`.
- **`resolve_template(name, repo_root)`** — **стек перевизначення шаблонів**: шукає назву
  шаблону за пріоритетом у: (1) `.specify/templates/overrides/`, (2) встановлених пресетах у
  `.specify/presets/<id>/templates/` (сортуються за полем `priority` у маніфесті `.registry`),
  (3) `.specify/extensions/<id>/templates/`, (4) основних `.specify/templates/`. Саме це
  дозволяє проєкту чи встановленому пресету/розширенню перевизначити стандартний
  `spec-template.md`, не торкаючись основного файлу.
- **`resolve_template_content(name, repo_root)`** — багатший варіант, що підтримує
  **стратегії композиції** поза простим «перевизначення виграє»: шар може заявити `replace`,
  `prepend`, `append` або `wrap` (з плейсхолдером `{CORE_TEMPLATE}`) у своєму маніфесті
  `preset.yml`, дозволяючи кільком шарам *об'єднуватись* в один шаблон, а не лише повністю
  замінювати інший.
- **`get_invoke_separator()` / `format_speckit_command()`** — читають `integration.json`, щоб
  відобразити правильне написання slash-команди для активної інтеграції (див. вище).
- **`json_escape()`** — чистий bash-екранувальник JSON-рядків (обробка керуючих символів за
  RFC 8259), що використовується як fallback, коли `jq` не встановлено.

### `create-new-feature.sh`

Викликається при визначенні нової фічі. Відповідальності:

- Генерує короткий, безпечний для бранчу суфікс із вільного текстового опису: переводить у
  нижній регістр, прибирає стоп-слова (артиклі, займенники, поширені дієслова), залишає значущі
  слова ≥3 символів (або коротші, якщо вони зустрічаються як великобуквений акронім в
  оригінальному тексті, наприклад «API»), склеює перші 3–4 через дефіс.
- Нумерує його: скановує `specs/` на наявні директорії `NNN-*` (ігноруючи директорії у стилі
  timestamp), бере найбільше знайдене число, інкрементує. Підтримує явне перевизначення
  `--number N`, що перерезолвиться до наступного вільного номера, якщо `N` вже зайнято (ніколи
  мовчки не перезаписує існуючу директорію специфікації).
- Застосовує обмеження GitHub на довжину назви бранчу (244 байти), обрізаючи суфікс (а не
  числовий префікс), якщо потрібно, з попередженням у stderr.
- Створює `specs/NNN-suffix/`, копіює резолвений `spec-template.md` у `spec.md`, якщо відсутній,
  і зберігає нову директорію фічі в `.specify/feature.json`.
- `--dry-run` обчислює назви/шляхи без torкання диска; `--allow-existing-branch` дозволяє
  викликачу повторно використати директорію, що вже існує, замість помилки.

### `check-prerequisites.sh`

«Вартовий», якого викликає кожен скіл пізнішого етапу перед будь-якою дією. Флаги:

- `--paths-only` — чисте резолвення шляхів, нуль валідації, використовується
  `speckit-clarify` на ранньому етапі.
- (без флагу) — вимагає існування `FEATURE_DIR` і `plan.md`; видає помилку, називаючи, який
  скіл слід запустити замість (`speckit-specify` / `speckit-plan`), якщо їх немає.
- `--require-tasks` — додатково вимагає існування `tasks.md` (використовується
  `speckit-implement`, `speckit-analyze`, `speckit-converge`, `speckit-taskstoissues`).
- `--include-tasks` — включає `tasks.md` у список `AVAILABLE_DOCS`, який повідомляється
  (окремо від *вимоги* його існування).

Видає або JSON-об'єкт (`--json`), або людиночитний текстовий блок зі списком знайдених
опційних документів (`research.md`, `data-model.md`, `contracts/`, `quickstart.md`,
`tasks.md`).

### `setup-plan.sh` / `setup-tasks.sh`

Тонкі обгортки, що використовуються відповідно `speckit-plan` / `speckit-tasks`: резолвлять
шляхи фічі, копіюють відповідний шаблон на місце, якщо цільовий файл ще не існує (ідемпотентно
— повторний запуск не затре існуючий `plan.md`), і видають JSON-payload, якого очікує скіл
(`FEATURE_SPEC`, `IMPL_PLAN`, `SPECS_DIR`, `BRANCH` для plan; `FEATURE_DIR`, `AVAILABLE_DOCS`,
`TASKS_TEMPLATE` для tasks).

## Шаблони (`.specify/templates/`)

Чотири канонічні скелети, кожен із жорсткою структурою секцій, яку заповнює відповідний скіл
(плейсхолдери у формі `[ALL_CAPS]` або `[у квадратних дужках]`):

- **`spec-template.md`** — `User Scenarios & Testing` (пріоритизовані, незалежно тестовані
  user stories зі сценаріями Given/When/Then), `Edge Cases`, `Requirements`
  (функціональні вимоги `FR-###`, `Key Entities`), `Success Criteria` (`SC-###`, мають бути
  вимірюваними та технологічно-нейтральними), `Assumptions`.
- **`plan-template.md`** — `Summary`, `Technical Context` (мова, залежності, сховище,
  тестування, платформа, продуктивність/масштаб), `Constitution Check` (ворітниця), `Project
  Structure` (з альтернативними варіантами компонування для single-project / web-app /
  mobile+API, невикористані скілом видаляються), `Complexity Tracking` (заповнюється лише якщо
  ворітниця конституції порушена, а порушення обґрунтовано, а не уникнено).
- **`tasks-template.md`** — структура по фазах: `Phase 1: Setup` → `Phase 2: Foundational
  (блокуюча)` → `Phase 3+: по одній фазі на user story, у порядку пріоритету` → `Final Phase:
  Polish`. Кожен рядок задачі — `- [ ] T### [P?] [USx?] Опис із точним шляхом файлу`.
- **`checklist-template.md`** — на нього посилається `speckit-checklist` щодо форматування
  заголовка/мета-даних/категорій; у разі відсутності використовується проста конвенція
  `## Category` + `- [ ] CHK### item`.

Проєкти/пресети/розширення можуть **перевизначати** будь-який із них (див. `resolve_template`
вище), не torкаючись основних копій — так організаційний пресет може, наприклад, додати
обов'язкову секцію «Observability» до кожного плану без форку самого Spec-Kit.

## Механізм хуків розширень (`.specify/extensions.yml`)

**Відсутній у цьому репозиторії**, але кожен скіл захищається від нього, тож варто
задокументувати: якщо `.specify/extensions.yml` існує, кожен скіл перевіряє записи під
ключем, специфічним для команди (`hooks.before_specify`, `hooks.after_plan` тощо). Кожен запис
хука може мати:

- `enabled: false` → пропускається (за замовчуванням увімкнено, якщо поле відсутнє).
- Непорожнє поле `condition` → скіл **не** намагається самостійно його оцінити; це залишено
  зовнішній реалізації `HookExecutor`.
- `optional: true` → скіл виводить хук як пропозицію (`Command: /{command}` + текст `Prompt:`)
  і чекає, доки користувач викличе його вручну.
- `optional: false` (обов'язковий) → скіл має реально його викликати (блок
  `EXECUTE_COMMAND:`) і заблокуватись на результаті перед продовженням.

Назви команд хуків пишуться через крапку (`speckit.git.commit`) у YAML, але відображаються з
роздільником активної інтеграції (`/speckit-git-commit` для цього проєкту на Claude Skills).
Канонічний приклад реального застосування цього механізму — **git-розширення**, що
створює/перемикає бранч фічі як хук `before_specify` — у цьому проєкті такого не встановлено,
тож `speckit-specify` створює директорію `specs/NNN-foo`, але **не** torкається git-бранчів.

## Декларативний воркфлоу (`.specify/workflows/speckit/workflow.yml`)

Опис вищого рівня (не виконуваний агентом) «повного циклу» (specify → plan → tasks → implement)
із двома людськими **ворітницями перегляду** (`type: gate`, `on_reject: abort`), вставленими
після specify та після plan. Цей файл — метадані для інструментарію оркестрації, що розуміє
Spec-Kit (наприклад, CI/автоматизаційний раннер, що веде весь конвеєр неінтерактивно); самі
Claude Skills його не читають — людина, що вручну викликає `/speckit-specify`,
`/speckit-clarify` тощо, фактично проходить той самий граф, де ворітниці перегляду — це
«чи людині достатньо подобається результат, щоб рухатись далі».

## Структура директорії фічі

```
specs/NNN-short-name/
├── spec.md                 # speckit-specify (+ speckit-clarify дописує)
├── checklists/
│   ├── requirements.md     # автостворюється speckit-specify, повторно перевіряється speckit-clarify
│   └── <domain>.md         # speckit-checklist, по одному файлу на кожен викликаний домен, append-only
├── plan.md                 # speckit-plan
├── research.md             # speckit-plan, Фаза 0
├── data-model.md           # speckit-plan, Фаза 1
├── contracts/               # speckit-plan, Фаза 1 (пропускається для суто внутрішніх фіч)
├── quickstart.md           # speckit-plan, Фаза 1 (путівник валідації/запуску, без коду реалізації)
└── tasks.md                # speckit-tasks (+ speckit-implement позначає [X], speckit-converge дописує)
```
