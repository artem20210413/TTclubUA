# Bootstrapping This Stack In A New Project

> Canonical (English) source of truth. See `BOOTSTRAP.uk.md` for a Ukrainian translation.

Everything described in `ARCHITECTURE.md` and `SKILLS.md` is the **stock, unmodified output**
of GitHub's `specify` CLI (the installer for [github/spec-kit](https://github.com/github/spec-kit)).
Nothing in `.specify/` or `.claude/skills/speckit-*/` was hand-written for this repository — it
was generated by running the installer and choosing Claude + Skills mode. Reproducing the stack
in a new project means running that installer again, not copying files by hand.

## 1. Prerequisites

- `git` (the installer and several helper scripts assume a git repo for root detection and
  branch-name length checks, though a git repo isn't strictly required to use Spec-Kit itself).
- `python3` recommended (used for JSON/YAML parsing in the template-resolution and
  invoke-separator helpers; there are `jq`/`awk` fallbacks if absent, so it's not a hard
  requirement, just reduces portability risk).
- `uv`/`uvx` (or `pip`) to run the `specify` CLI without a permanent install.
- Claude Code with Skills support (this project uses `ai_skills: true` — the Skills mechanism,
  not flat slash-command files).

## 2. Run the installer

For a brand-new project directory:

```bash
uvx --from git+https://github.com/github/spec-kit.git specify init <project-name> --ai claude
```

For an **existing** repository (the situation for this Laravel app — Spec-Kit was layered onto
an already-running codebase):

```bash
cd <existing-project>
uvx --from git+https://github.com/github/spec-kit.git specify init --here --ai claude
```

During/after init, confirm or select:

- **AI integration**: `claude` (produces `.claude/skills/speckit-*/SKILL.md`; other values
  produce the equivalent for Copilot/Gemini/opencode/etc. in their own command directories).
- **Skills vs. commands**: make sure Skills mode is enabled (`ai_skills: true` in the resulting
  `.specify/init-options.json`) rather than flat markdown slash commands, if the installer asks.
- **Feature numbering**: `sequential` (`specs/001-foo`, `002-bar`, …) is what this project uses
  and is the sane default for a single team working linearly; pick `timestamp` instead if
  multiple contributors might create features concurrently and sequential numbers would race.

This produces exactly the tree described in README.md's "Directory map": `.specify/` (config,
scripts, templates, empty `memory/constitution.md` template) and `.claude/skills/speckit-*/`
(the 10 skill definitions). **`specs/` is not created yet** — it appears on the first
`/speckit-specify` invocation.

## 3. Write a real constitution (don't copy this repo's)

Run `/speckit-constitution` and describe the **new** project's actual non-negotiables — team
size, framework, testing discipline, anything that should gate every `/speckit-plan`. This
repo's constitution (Simplicity & YAGNI + Laravel & Framework Conventions — see
`.specify/memory/constitution.md`) is tailored to a small Laravel team and should not be reused
verbatim for a different stack or team size; `/speckit-constitution` will derive fresh
principles from what you actually tell it about the new project.

## 4. Drive one feature through the full pipeline

```text
/speckit-specify "<plain-language description of the feature>"
/speckit-clarify
/speckit-plan
/speckit-tasks
/speckit-checklist <domain>      # optional, repeat per domain (ux, api, security, …)
/speckit-analyze                 # optional, read-only sanity check before implementing
/speckit-implement
/speckit-converge                # optional, run again after implement to catch drift
/speckit-taskstoissues            # optional, only if the remote is actually GitHub
```

Each command's own prerequisite check will refuse to run and name the correct prior command if
something upstream is missing, so there's little risk of getting the order wrong by accident.

## 5. Optional: the extension-hooks layer

If the new project wants automation around the pipeline (e.g. auto-creating/switching a git
branch per feature, auto-committing after each stage, posting to Slack on completion), author a
`.specify/extensions.yml` with `hooks.before_<command>` / `hooks.after_<command>` entries. Every
skill already contains the dispatch logic for this (see ARCHITECTURE.md's "extension-hooks
mechanism" section) — nothing in the skill files themselves needs to change; adding the YAML is
enough. This repository does not use this layer today.

## 6. Optional: project-local conventions worth carrying over

Two things in this repo are **not** part of stock Spec-Kit but are worth deliberately deciding
on for a new project, since they shape day-to-day usage:

- **Bilingual artifact mirrors**: this project keeps a `*.uk.md` Ukrainian translation
  alongside every English artifact produced under `specs/<feature>/` (and, by the same
  convention, alongside documents like this one). This is a locally-adopted habit, not
  something Spec-Kit generates — decide per-project whether it's worth the upkeep.
- **Constitution-driven code review**: this repo's constitution explicitly tells reviewers to
  check PRs for Simplicity & YAGNI and Laravel-convention compliance. Writing the constitution
  with review-time enforcement in mind (not just planning-time gates) makes it pull more weight
  than treating it as a one-off ratified document.

## 7. Keeping the stack itself up to date

The installed version is pinned in `.specify/init-options.json`'s `speckit_version`
(`0.14.2.dev0` for this repo). Re-running the installer (`specify init --here` again, or its
`upgrade` equivalent if the CLI exposes one) picks up newer core templates/scripts — but any
**project overrides** under `.specify/templates/overrides/` are designed to survive that, since
they sit above the core layer in the resolution stack described in ARCHITECTURE.md.
