# Встановлення цього стеку в новому проєкті

> Переклад українською. Канонічним джерелом істини є `BOOTSTRAP.md` (англійською).

Усе, описане в `ARCHITECTURE.md` та `SKILLS.md`, — це **стандартний, незмінений вивід**
інсталятора `specify` від GitHub (установник для [github/spec-kit](https://github.com/github/spec-kit)).
Нічого в `.specify/` чи `.claude/skills/speckit-*/` не написано вручну для цього репозиторію —
усе згенеровано запуском інсталятора з вибором Claude + режиму Skills. Відтворити цей стек у
новому проєкті означає знову запустити цей інсталятор, а не копіювати файли вручну.

## 1. Передумови

- `git` (інсталятор і кілька хелпер-скриптів припускають git-репозиторій для виявлення
  кореня та перевірки довжини назви бранчу, хоча git-репозиторій не є суворо обов'язковим для
  самого Spec-Kit).
- `python3` рекомендовано (використовується для парсингу JSON/YAML у хелперах резолюції
  шаблонів та роздільника викликів; є fallback-и на `jq`/`awk` за відсутності, тож це не
  жорстка вимога, лише зменшує ризик проблем із портативністю).
- `uv`/`uvx` (або `pip`) для запуску CLI `specify` без постійної установки.
- Claude Code з підтримкою Skills (цей проєкт використовує `ai_skills: true` — механізм
  Skills, а не плоскі файли slash-команд).

## 2. Запустити інсталятор

Для зовсім нової директорії проєкту:

```bash
uvx --from git+https://github.com/github/spec-kit.git specify init <project-name> --ai claude
```

Для **існуючого** репозиторію (саме ситуація для цього Laravel-застосунку — Spec-Kit був
доданий до вже працюючої кодової бази):

```bash
cd <existing-project>
uvx --from git+https://github.com/github/spec-kit.git specify init --here --ai claude
```

Під час/після init підтвердіть або оберіть:

- **AI-інтеграція**: `claude` (створює `.claude/skills/speckit-*/SKILL.md`; інші значення
  створюють еквівалент для Copilot/Gemini/opencode/тощо у їхніх власних директоріях команд).
- **Skills проти команд**: переконайтесь, що режим Skills увімкнено (`ai_skills: true` у
  результуючому `.specify/init-options.json`), а не плоскі markdown slash-команди, якщо
  інсталятор про це питає.
- **Нумерація фіч**: `sequential` (`specs/001-foo`, `002-bar`, …) — те, що використовує цей
  проєкт, і розумний дефолт для однієї команди, що працює лінійно; оберіть `timestamp`
  замість цього, якщо кілька учасників можуть створювати фічі одночасно і послідовні номери
  могли б конфліктувати.

Це створює саме те дерево, що описане в розділі «Карта директорій» файлу README.md:
`.specify/` (конфігурація, скрипти, шаблони, порожній шаблон `memory/constitution.md`) та
`.claude/skills/speckit-*/` (10 визначень скілів). **`specs/` ще не створюється** — вона
з'являється при першому виклику `/speckit-specify`.

## 3. Написати справжню конституцію (не копіювати конституцію цього репозиторію)

Запустіть `/speckit-constitution` і опишіть реальні незаперечні принципи **нового** проєкту —
розмір команди, фреймворк, дисципліну тестування, усе, що має фільтрувати кожен
`/speckit-plan`. Конституція цього репозиторію (Simplicity & YAGNI + Laravel & Framework
Conventions — див. `.specify/memory/constitution.md`) підлаштована під малу Laravel-команду і
не повинна буквально переноситись на інший стек чи розмір команди; `/speckit-constitution`
виведе свіжі принципи з того, що ви реально розкажете про новий проєкт.

## 4. Провести одну фічу через повний конвеєр

```text
/speckit-specify "<опис фічі звичайною мовою>"
/speckit-clarify
/speckit-plan
/speckit-tasks
/speckit-checklist <domain>      # опційно, повторювати для кожного домену (ux, api, security, …)
/speckit-analyze                 # опційно, read-only перевірка здорового глузду перед implement
/speckit-implement
/speckit-converge                # опційно, запустити знову після implement, щоб виявити розбіжності
/speckit-taskstoissues            # опційно, лише якщо рімоут — справді GitHub
```

Власна перевірка передумов кожної команди відмовиться виконуватись і назве правильну
попередню команду, якщо чогось не вистачає вище по конвеєру, тож ризик переплутати порядок
випадково мінімальний.

## 5. Опційно: шар хуків розширень

Якщо новий проєкт хоче автоматизацію навколо конвеєра (наприклад, автостворення/перемикання
git-бранчу на фічу, автокоміт після кожного етапу, публікація у Slack при завершенні),
напишіть `.specify/extensions.yml` із записами `hooks.before_<command>` /
`hooks.after_<command>`. Кожен скіл уже містить логіку диспетчеризації для цього (див. розділ
«Механізм хуків розширень» у ARCHITECTURE.md) — нічого в самих файлах скілів змінювати не
потрібно; достатньо додати YAML. Цей репозиторій наразі не використовує цей шар.

## 6. Опційно: локальні конвенції проєкту, варті перенесення

Дві речі в цьому репозиторії **не** є частиною стандартного Spec-Kit, але варті свідомого
рішення для нового проєкту, оскільки вони формують щоденне використання:

- **Двомовні дзеркала артефактів**: цей проєкт зберігає переклад `*.uk.md` українською поруч
  із кожним англійським артефактом, створеним під `specs/<feature>/` (і, за тією ж
  конвенцією, поруч із документами, подібними до цього). Це локально прийнята звичка, а не
  щось, що генерує Spec-Kit — вирішуйте окремо для кожного проєкту, чи варте це підтримки.
- **Рев'ю коду на основі конституції**: конституція цього репозиторію явно каже рев'юєрам
  перевіряти PR на відповідність Simplicity & YAGNI та конвенціям Laravel. Написання
  конституції з орієнтацією на застосування під час рев'ю (а не лише як ворітниця під час
  планування) робить її вагомішою, ніж якщо ставитись до неї як до одноразового
  ратифікованого документа.

## 7. Підтримка стеку в актуальному стані

Встановлена версія зафіксована у `speckit_version` файлу `.specify/init-options.json`
(`0.14.2.dev0` для цього репозиторію). Повторний запуск інсталятора (знову `specify init
--here`, чи еквівалент `upgrade`, якщо CLI його надає) підхоплює новіші основні шаблони/
скрипти — але будь-які **проєктні перевизначення** під `.specify/templates/overrides/`
розраховані на те, щоб переживати це, оскільки вони лежать над основним шаром у стеку
резолюції, описаному в ARCHITECTURE.md.
