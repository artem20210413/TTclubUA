# Глибокий розбір 10 скілів

> Переклад українською. Канонічним джерелом істини є `SKILLS.md` (англійською).
>
> Кожен скіл визначено у `.claude/skills/speckit-<name>/SKILL.md`. Усі вони мають спільну
> «обгортку», яка не повторюється нижче окремо для кожного скілу (див. «Спільна обгортка» в
> кінці): блок вхідних даних користувача `$ARGUMENTS`, крок **Pre-Execution Checks**, що шукає
> хуки в `.specify/extensions.yml`, і крок **Mandatory/Post-Execution Hooks** наприкінці, що
> робить те саме для хуків `after_*`. Тут документується лише *відмінна* логіка кожного скілу.

## 0. `speckit-constitution`

**Одним рядком**: Створити або оновити конституцію проєкту з інтерактивних або наданих
принципів, забезпечуючи синхронність усіх залежних шаблонів.

**Коли**: Один раз при налаштуванні проєкту, і знову будь-коли при зміні керівних принципів. Не
входить у поетапний конвеєр по фічах.

**Захист обсягу (scope guard)**: це єдиний скіл з явним убудованим правилом проти розповзання
обсягу — якщо вхід користувача змішує контент конституції з непов'язаним запитом («а ще
реалізуй X поки ти тут»), скіл **не повинен** виконувати непов'язану частину. Він класифікує
кожну частину входу як контент конституції чи відкладений намір, і перелічує відкладені наміри
у секції `Next Actions` наприкінці (пропонуючи правильну наступну команду, наприклад
`/speckit-specify`, без її виклику).

**Алгоритм**:
1. Завантажити `.specify/memory/constitution.md` (при першому запуску — шаблон із
   плейсхолдерами `[ALL_CAPS]`).
2. Заповнити кожен плейсхолдер із входу користувача, за відсутності — з контексту репозиторію
   (README, попередній текст конституції). Дати мають бути у форматі ISO (`YYYY-MM-DD`);
   невідомі дати стають `TODO(FIELD_NAME): пояснення`, а не вгадуються.
3. Визначити semver-зсув: MAJOR для несумісного видалення/перевизначення принципу, MINOR для
   нового/суттєво розширеного принципу, PATCH лише для змін формулювання. Якщо неоднозначно,
   скіл має викласти своє обґрунтування перед остаточним рішенням — не вибирає мовчки.
4. **Чекліст поширення** — повторно прочитати й узгодити з новими принципами:
   - секцію ворітниці Constitution Check у `.specify/templates/plan-template.md`
   - секції обсягу/вимог у `.specify/templates/spec-template.md`
   - категоризацію задач у `.specify/templates/tasks-template.md`
   - кожен інший файл скілу `speckit-*`, щоби виявити застарілі агент-специфічні посилання
   - будь-яку документацію верхнього рівня (README.md, quickstart-документи)
5. Додати перед файлом **Sync Impact Report** (HTML-коментар): версія стара→нова, принципи
   додані/змінені/видалені, які шаблони перевірено (✅/⚠), залишкові TODO.
6. Перевірити: не лишилось непоясненних токенів у дужках, дати в ISO, принципи
   декларативні/тестовані (не «should» без обґрунтування MUST/SHOULD).
7. Перезаписати `.specify/memory/constitution.md` — цей скіл **ніколи** не створює новий файл,
   лише редагує один канонічний файл конституції.
8. Звіт: нова версія + обґрунтування зсуву, файли, позначені для ручного опрацювання,
   пропонований commit-message, і блок `Next Actions` для відкладених намірів (якщо є).

**Жорстке обмеження**: не повинен створювати/змінювати/видаляти файли вихідного коду
застосунку, маршрути, компоненти, тести чи файли деплою — ніколи, незалежно від того, що міститься
у вході користувача.

## 1. `speckit-specify`

**Одним рядком**: Створити або оновити специфікацію фічі з опису природною мовою.

**Коли**: Старт нової фічі. Перша команда поетапного конвеєра для фічі.

**Алгоритм**:
1. Вивести **коротку назву з 2–4 слів** з опису (у стилі дія-іменник, зі збереженням
   акронімів: «Implement OAuth2 integration for the API» → `oauth2-api-integration`).
2. Якщо виконався хук розширення `before_specify` (наприклад, git-розширення), врахувати
   `BRANCH_NAME`/`FEATURE_NUM`, які він повернув — але **назва директорії специфікації не
   залежить від назви git-бранчу**, ця команда ніколи не диктує й не вимагає конкретного
   бранчу.
3. Резолвити `SPECIFY_FEATURE_DIRECTORY`: явне перевизначення виграє; інакше автогенерація під
   `specs/` за допомогою `feature_numbering` з `init-options.json` (`sequential` — 3-значний
   префікс через сканування існуючих директорій, або `timestamp` — `YYYYMMDD-HHMMSS`).
   `mkdir`, скопіювати резолвений `spec-template.md` у `spec.md`, зберегти шлях у
   `.specify/feature.json`. **Рівно одна фіча на виклик.**
4. Завантажити шаблон специфікації + (якщо є) конституцію, потім заповнити шаблон:
   - Виокремити акторів/дії/дані/обмеження з опису.
   - Для неясних моментів зробити обґрунтоване припущення за замовчуванням; видавати
     `[NEEDS CLARIFICATION: ...]` лише коли вибір суттєво змінює обсяг/UX і немає жодного
     розумного значення за замовчуванням. **Жорсткий ліміт: 3 маркери**, пріоритет: обсяг >
     безпека/приватність > UX > технічні деталі.
   - Заповнити User Scenarios (пріоритизовані, незалежно тестовані user stories зі сценаріями
     Given/When/Then), Functional Requirements (`FR-###`, кожна тестована), Success Criteria
     (`SC-###`, вимірювані **і технологічно-нейтральні** — «Користувачі завершують оформлення
     замовлення менш ніж за 3 хвилини», ніколи «API відповідає за <200ms»), Key Entities,
     Assumptions.
5. **Самоперевірка якості**: згенерувати `checklists/requirements.md` (чекбокси Content
   Quality / Requirement Completeness / Feature Readiness) і оцінити специфікацію проти нього,
   до 3 ітерацій виправлення. Будь-які залишкові маркери `[NEEDS CLARIFICATION]` виносяться
   користувачу як **нумерований, максимум-3, у форматі таблиці** набір питань з варіантами
   вибору (з явним рядком «Custom») — усі відповідаються разом, потім вплітаються назад у
   специфікацію, після чого чекліст перевіряється знову.
6. Звіт: директорія фічі, шлях до файлу специфікації, підсумок проходження чекліста, і чи
   наступний крок — `/speckit-clarify`, чи напряму `/speckit-plan`.

**Примітка**: створення бранчу явно **не** є завданням цієї команди (це робота
git-розширення, через хук) — директорія та файл специфікації завжди створюються тут незалежно
від хуків.

## 2. `speckit-clarify`

**Одним рядком**: Виявити недостатньо специфіковані ділянки у поточній специфікації фічі,
задавши до 5 вузько цільових уточнюючих питань, і закодувати відповіді назад у специфікацію.

**Коли**: Відразу після specify, перед plan. Очікується (але не вимагається жорстко) виконання
перед `/speckit-plan` — пропуск дозволений для розвідувальних спайків, але скіл має
попередити про підвищений ризик перероблення, якщо так зроблено.

**Алгоритм**:
1. Один раз `check-prerequisites.sh --json --paths-only`, щоб отримати
   `FEATURE_DIR`/`FEATURE_SPEC`.
2. Просканувати специфікацію за **11-категорійною таксономією неоднозначностей**
   (Функціональний обсяг, Домен і модель даних, Взаємодія та UX, Нефункціональна якість,
   Інтеграція та зовнішні залежності, Крайні випадки й обробка відмов, Обмеження й компроміси,
   Термінологія, Сигнали завершеності, Інше/плейсхолдери), позначаючи кожну як
   Чітко/Частково/Відсутньо. Ця карта внутрішня — ніколи не виводиться сирцем, якщо не буде
   задано нуль питань.
3. Побудувати **пріоритизовану черга ≤5 кандидатних питань** із категорій
   Частково/Відсутньо, кожне відповідне або як вибір із 2–5 варіантів, або як коротка
   відповідь ≤5 слів. Виключити все, що не змінило б архітектуру/модель даних/тести/UX/
   операції/комплаєнс.
4. **Задавати по одному питанню за раз.** Для варіантів вибору: обчислити й подати на початку
   рядок `**Recommended:** Option X — обґрунтування`, потім markdown-таблицю варіантів (з
   вільним рядком "Short"), і приймати «yes»/«recommended» як згоду з рекомендацією. Для
   короткої відповіді: подати на початку `**Suggested:** ... — обґрунтування`. Зупинитись
   раніше, якщо залишкові неоднозначності вирішуються самі, користувач сигналізує «done», або
   задано 5 питань — залежно від того, що настане першим. Ніколи не розкривати питання в черзі,
   які ще не задані.
5. **Після кожної прийнятої відповіді** (не пакетно наприкінці): додати
   `- Q: <питання> → A: <відповідь>` під секцією `## Clarifications` /
   `### Session YYYY-MM-DD`, потім негайно вплести відповідь у *найбільш релевантну* існуючу
   секцію (Functional Requirements / User Stories / Data Model / Success Criteria / Edge
   Cases / нормалізація термінології — замінюючи протилежний текст, а не дописуючи поруч),
   потім **негайно зберегти файл** (атомарні записи після кожної відповіді, а не один запис
   наприкінці, щоб переживати обірвану сесію).
6. Повторно перевірити `checklists/requirements.md`, якщо наявний: перерахувати кожен чекбокс
   проти *оновленої* специфікації, перемкнути лише ті, стан яких дійсно змінився, і звітувати
   **нові проходження** проти **регресії** (був позначений → знову не позначений) проти
   **ще не позначені**.
7. Звіт: скільки питань задано/відповідено, які секції торкнуто, кількість чекліста до/після,
   таблиця покриття за категоріями (Вирішено / Відкладено / Чітко / Невирішено), рекомендація
   щодо продовження до `/speckit-plan` чи повторного clarify пізніше.

**Жорсткі обмеження**: ніколи більше 5 прийнятих питань загалом; якщо файл специфікації
відсутній — повідомити користувачу запустити `/speckit-specify`, цей скіл ніколи не створює
специфікацію.

## 3. `speckit-plan`

**Одним рядком**: Виконати воркфлоу планування реалізації, використовуючи шаблон плану для
генерації проєктних артефактів.

**Коли**: Коли специфікація зрозуміла (бажано після clarify).

**Алгоритм**:
1. `setup-plan.sh --json` → `FEATURE_SPEC`, `IMPL_PLAN`, `SPECS_DIR`, `BRANCH` (ідемпотентно
   копіює `plan-template.md` у `plan.md`, якщо ще не присутній).
2. Завантажити специфікацію + конституцію.
3. Заповнити **Technical Context** шаблону плану (мова, залежності, сховище, тестування,
   платформа, продуктивність/масштаб — усе невідоме позначити як `NEEDS CLARIFICATION`),
   потім ворітницю **Constitution Check** проти реальних принципів проєкту (ERROR на
   необґрунтоване порушення — обґрунтування, якщо є, йде в таблицю **Complexity Tracking**,
   що є *єдиним* способом пройти повз провал ворітниці, окрім спрощення підходу).
4. **Фаза 0 — Дослідження**: для кожного `NEEDS CLARIFICATION` і кожної помітної
   залежності/інтеграції запустити дослідницьку задачу («Research X for Y», «Find best
   practices for Z in domain W»), об'єднати у `research.md` як трійки
   Рішення / Обґрунтування / Розглянуті альтернативи. Результат має залишити **нуль**
   невирішених маркерів `NEEDS CLARIFICATION` у Technical Context.
5. **Фаза 1 — Дизайн і контракти** (передумова: research.md завершено):
   - `data-model.md`: сутності + поля + зв'язки + правила валідації + переходи стану, витягнуті
     зі специфікації.
   - `contracts/`: по одному файлу на кожен зовнішньо-експонований інтерфейс (REST-ендпоінти,
     схеми CLI-команд, публічні бібліотечні API, UI-контракти — все, що відкриває назовні тип
     проєкту). **Повністю пропускається** для суто внутрішніх проєктів (скрипти збірки,
     одноразові інструменти).
   - `quickstart.md`: *путівник валідації, придатний для запуску* (передумови, команди
     налаштування/запуску, очікувані результати), який **не повинен** містити повний код
     реалізації, тіла моделей/сервісів, міграції чи набори тестів — це робота `tasks.md` та
     `speckit-implement`.
   - Повторно виконати Constitution Check після дизайну (дизайн може внести порушення, яких не
     було у початковому Technical Context).
6. Звіт: бранч, шлях `plan.md`, і список згенерованих артефактів. Нічого не рухається далі
   через провал ворітниці чи невирішену неоднозначність — ця команда завершується з помилкою,
   а не вгадує.

## 4. `speckit-tasks`

**Одним рядком**: Згенерувати дієвий, впорядкований за залежностями `tasks.md` для фічі на
основі наявних проєктних артефактів.

**Коли**: Після того, як існує plan.md.

**Алгоритм**:
1. `setup-tasks.sh --json` → `FEATURE_DIR`, `TASKS_TEMPLATE` (резолвений через стек
   перевизначення — жорстка помилка, якщо `tasks-template` не резолвиться ніде),
   `AVAILABLE_DOCS`.
2. **Обов'язково**: `plan.md` (технічний стек, структура) + `spec.md` (пріоритизовані user
   stories). **Опційно, якщо є**: `data-model.md` (сутності), `contracts/` (інтерфейси),
   `research.md` (рішення для задач налаштування), `constitution.md`.
3. **Головна вісь організації — user story**, а не архітектурний шар. Для кожної історії
   `P1`/`P2`/`P3`… зі spec.md: зібрати моделі/сервіси/ендпоінти/UI, потрібні для неї (зіставлені
   з data-model.md/contracts/), в одну самодостатню фазу. Тести генеруються **лише якщо явно
   запитані** (запит на TDD, або цього вимагає специфікація) — вони не є дефолтом.
4. **Формат чекліста — непорушний** для кожного рядка задачі:
   `- [ ] T### [P?] [USx?] Опис із точним шляхом файлу`
   - `T###` послідовний, у порядку виконання.
   - `[P]` присутній лише якщо задача torкається інших файлів без залежності від незавершеної
     задачі.
   - `[USx]` присутній **лише** всередині фази user story (ніколи у Setup/Foundational/
     Polish).
   - Шлях файлу обов'язковий в описі — «Create User model» без шляху — некоректний вивід.
5. **Структура фаз**: `Phase 1: Setup` → `Phase 2: Foundational` (блокуюча, має завершитись
   перед *будь-якою* історією) → `Phase 3+`: по одній фазі на user story в порядку пріоритету
   (всередині кожної: Tests[якщо запитані] → Models → Services → Endpoints → Integration) →
   `Final Phase: Polish & Cross-Cutting`.
6. Видати секцію залежностей (порядок фаз + примітки про незалежність по історіях), приклади
   паралельного виконання по кожній історії, і блок "Implementation Strategy", що рекомендує
   MVP-first (лише Setup+Foundational+Story-1) потім інкрементальну доставку наступних історій.
7. Звіт: загальна кількість задач, розбивка по історіях, виявлені можливості паралелізації,
   пропонований MVP-обсяг (типово — лише User Story 1), і явне підтвердження валідації
   формату.

**Задум дизайну**: кожна задача має бути достатньо конкретною, щоб LLM міг виконати її без
*додаткового* контексту, окрім рядка задачі та задекларованих проєктних документів.

## 5. `speckit-checklist`

**Одним рядком**: Згенерувати кастомний чекліст для поточної фічі на основі вимог користувача.

**Коли**: Будь-коли після наявності специфікації; повторюваний; різні домени отримують різні
файли.

**Основна концепція — «юніт-тести для англійської»**: пункт чекліста перевіряє *якість
формулювання вимоги*, **а не** чи працює реалізація. Це найважливіше та найчастіше порушуване
правило цього скілу, тож варто наголосити:

| ❌ Неправильно (тестує реалізацію) | ✅ Правильно (тестує якість вимоги) |
|---|---|
| «Verify landing page displays 3 episode cards» | «Are the exact number and layout of featured episodes specified? [Completeness]» |
| «Test hover states work on desktop» | «Are hover-state requirements consistently defined across all interactive elements? [Consistency]» |
| «Confirm logo click navigates home» | «Are navigation requirements clear for all clickable brand elements? [Clarity]» |

Заборонені дієслова у будь-якому пункті: «Verify», «Test», «Confirm», «Check» + поведінка
реалізації; заборонені фрази: «displays correctly», «works properly», «click», «navigate»,
«render», «load», «execute». Потрібний шаблон: «Are/Is [вимога] defined/specified/quantified/
consistent/measurable for [сценарій]?»

**Алгоритм**:
1. `check-prerequisites.sh --json` для `FEATURE_DIR` + `AVAILABLE_DOCS`.
2. Задати **до 3** динамічно згенерованих уточнюючих питань (ніколи заздалегідь заготовлений
   каталог) щодо обсягу/глибини/аудиторії, виведених із аналізу сигналів у фразуванні самого
   користувача — пропустити будь-яке питання, на яке вже відповів сам ввід користувача. Можна
   розширити до 2 додаткових (максимум 5) лише якщо ≥2 класи сценаріїв (Alternate/Exception/
   Recovery/Non-Functional) залишаються неясними після першого раунду, кожне додаткове питання
   обґрунтоване одним рядком.
3. Завантажити spec/plan/tasks (лише ті частини, що релевантні обраним областям фокусу —
   підсумовувати, а не виводити повні файли).
4. **Генерація файлу**: `FEATURE_DIR/checklists/<domain>.md` (наприклад, `ux.md`, `api.md`,
   `security.md`, `performance.md`). Якщо не існує — почати нумерацію з `CHK001`; якщо
   існує — **дописати**, продовжуючи з останнього наявного `CHK###` — існуючий контент ніколи
   не видаляється й не перезаписується.
5. Категорії: Requirement Completeness, Clarity, Consistency, Acceptance Criteria Quality,
   Scenario Coverage, Edge Case Coverage, Non-Functional Requirements, Dependencies &
   Assumptions, Ambiguities & Conflicts.
6. **Трасованість**: ≥80% пунктів мають посилатись або на секцію специфікації
   (`[Spec §FR-5]`), або на маркер (`[Gap]`, `[Ambiguity]`, `[Conflict]`, `[Assumption]`).
   М'який ліміт ~40 сирих пунктів перед консолідацією за ризиком/впливом; >5 малозначних
   крайніх випадків згортаються в один пункт.
7. Звіт: повний шлях, кількість пунктів, новий файл чи дописано, обрані фокус-області/глибина/
   аудиторія.

## 6. `speckit-analyze`

**Одним рядком**: Виконати неруйнівний аналіз узгодженості та якості між `spec.md`, `plan.md`
та `tasks.md` після генерації задач.

**Коли**: Після `speckit-tasks`, перед `speckit-implement`. **Строго read-only** — це єдиний
скіл у наборі, якому контрактно заборонено писати будь-який файл; він видає звіт у чаті і,
опційно за явним підтвердженням користувача, *пропонує* виправлення (але не застосовує їх у
цьому виклику).

**Алгоритм**:
1. `check-prerequisites.sh --json --require-tasks --include-tasks`, жорстке переривання з
   назвою відсутньої передумовної команди, якщо `spec.md`/`plan.md`/`tasks.md` не всі наявні.
2. Завантажити поступово (не повні дампи файлів): Overview/FRs/SCs/UserStories/EdgeCases зі
   специфікації; architecture/data-model-refs/phases/constraints з плану; IDs/descriptions/
   phase/`[P]`/file-paths із задач; назви принципів + твердження MUST/SHOULD з конституції.
3. Побудувати внутрішні семантичні моделі (ніколи не виводяться сирцем): реєстр вимог,
   ключований за `FR-###`/`SC-###` (SC обмежені лише такими, що вимагають *реалізовуваної*
   роботи — виключаючи показники у стилі бізнес-KPI, як «зменшити кількість звернень у
   підтримку на 50%»), карту покриття задачами, набір правил конституції.
4. **Шість проходів виявлення**: (A) Дублювання — майже-дублікати вимог; (B) Неоднозначність —
   нечіткі прикметники («fast», «scalable», «secure», «intuitive») і невирішені плейсхолдери
   (`TODO`, `???`); (C) Недоспецифікованість — дієслова без вимірюваного об'єкта, задачі з
   посиланнями на невизначені файли/компоненти; (D) Відповідність конституції — усе, що
   конфліктує з MUST; (E) Прогалини покриття — вимоги без жодної задачі, задачі без вимоги,
   реалізовувані SC без задачі; (F) Неузгодженість — дрейф термінології, сутності в плані, але
   не в специфікації (чи навпаки), протиріччя в порядку, прямо конфліктуючі вимоги (наприклад,
   «Next.js» проти «Vue» у різних файлах).
5. **Серйозність**: CRITICAL (порушення MUST конституції, відсутній основний артефакт, вимога
   з нульовим покриттям, що блокує базову функціональність) > HIGH (дубльована/конфліктуюча
   вимога, неоднозначний атрибут безпеки/продуктивності, нетестований критерій прийняття) >
   MEDIUM (дрейф термінології, відсутнє нефункціональне покриття) > LOW (лише формулювання).
6. Видати одну markdown-таблицю (максимум 50 рядків, надлишок підсумовується), таблицю
   покриття вимог, список відповідності конституції, список неприв'язаних задач, і підсумкові
   метрики (загальна кількість вимог/задач, % покриття, кількість неоднозначностей/
   дублювань/критичних проблем).
7. Завершити явним блоком **Next Actions** (яку команду перезапустити для якого виправлення)
   та пропозицією: «Would you like me to suggest concrete remediation edits for the top N
   issues?» — ніколи не застосовується автоматично.

## 7. `speckit-implement`

**Одним рядком**: Виконати план реалізації, обробивши й виконавши всі задачі, визначені у
`tasks.md`.

**Коли**: Коли tasks.md (і бажано чеклісти) готові. Це єдиний скіл, що пише вихідний код
застосунку.

**Алгоритм**:
1. `check-prerequisites.sh --json --require-tasks --include-tasks`.
2. **Ворітниця чеклістів**: якщо `checklists/` існує, підрахувати total/completed/incomplete
   по кожному файлу в таблицю статусу. Якщо у будь-якому чекcліcті є незавершені пункти:
   показати таблицю, **зупинитись**, і явно запитати у користувача «продовжити попри це?
   (yes/no)» — продовжувати лише при позитивній відповіді. Якщо всі пройшли: показати таблицю
   й автоматично продовжити.
3. Завантажити `tasks.md` (обов'язково), `plan.md` (обов'язково), і все з наявних
   `data-model.md`/`contracts/`/`research.md`/`constitution.md`/`quickstart.md`.
4. **Перевірка налаштування проєкту**: виявити реально наявний стек (git-репозиторій?
   Dockerfile? `.eslintrc*`? `.prettierrc*`? `*.tf`? helm-чарти?) і створити/перевірити
   відповідний ignore-файл (`.gitignore`, `.dockerignore`, `.eslintignore`,
   `.prettierignore`, `.npmignore`, `.terraformignore`, `.helmignore`) із правильними
   шаблонами для *цієї* технології — дописати відсутні критичні шаблони до існуючого файлу,
   а не перезаписати його.
5. Розпарсити фази/залежності/маркери `[P]`/шляхи файлів із `tasks.md`, потім виконувати
   **фазу за фазою**: завершити фазу повністю перед початком наступної; всередині фази —
   запускати задачі `[P]` разом, а послідовні — по порядку; якщо тести запитані, вони
   виконуються *перед* відповідною задачею реалізації (TDD); задачі, що torкаються одного
   файлу, не повинні запускатись паралельно.
6. Обробка прогресу/помилок: звітувати після кожної завершеної задачі; **зупинитись** при
   провалі непараленьної задачі; для провалу задачі `[P]` — продовжити з іншими й окремо
   звітувати провал; **позначити завершені задачі `[X]` у `tasks.md`** по мірі завершення
   (саме так `speckit-converge` і повторний запуск `speckit-implement` знають, що
   залишилось).
7. Фінальна перевірка: усі обов'язкові задачі завершені, реалізація відповідає специфікації,
   тести (якщо є) проходять, технічні рішення плану дійсно дотримані.

## 8. `speckit-converge`

**Одним рядком**: Оцінити поточну кодову базу проти специфікації, плану та задач фічі, потім
дописати будь-яку залишкову непобудовану роботу як нові задачі в `tasks.md`, щоб implement міг
її завершити.

**Коли**: Після принаймні одного проходу `speckit-implement`, для виявлення розбіжностей.
**Це не інструмент git diff** — він перевіряє *поточний стан* коду проти *поточних*
артефактів, без урахування історії/бранчів.

**Обмеження роботи — лише дописування, ніколи перезапис**: **єдиний** запис, який цьому скілу
дозволено робити — дописати одну нову секцію `## Phase N: Convergence` в кінець `tasks.md`.
Він ніколи не повинен torкатися `spec.md`/`plan.md`, ніколи перенумеровувати/переставляти/
видаляти жодну існуючу задачу (включно з задачами з *попередньої* фази Convergence), і ніколи
торкатись коду застосунку безпосередньо — виправлення прогалини є роботою `speckit-implement`
при наступному запуску. Якщо нічого не бракує, `tasks.md` має вийти **байт-у-байт незмінним**
(навіть без порожнього заголовка).

**Алгоритм**:
1. `check-prerequisites.sh --json --require-tasks --include-tasks`; жорстка зупинка з назвою
   відсутньої передумовної команди, якщо spec/plan/tasks не всі наявні — без часткового
   виводу.
2. Завантажити специфікацію (FR, реалізовувані SC, сценарії прийняття user story, крайні
   випадки), план (архітектура/посилання на модель даних/фази/названі точки дотику), задачі
   (ID — для обчислення наступного ID і номера фази), конституцію (якщо вона не є ще
   незаповненим шаблоном, у такому разі перевірки конституції пропускаються без помилки).
3. Побудувати **реєстр намірів** (один стабільний ключ на кожен FR/SC/сценарій прийняття,
   плюс рішення плану та MUST-принципи конституції) та **карту обсягу коду** (із шляхів
   файлів, названих у plan.md та tasks.md, плюс пошук за ключовими словами понять, які
   описують вимоги) — оцінка обмежена цим обсягом; не повинна виводити обсяг за межі того, що
   визначають артефакти.
4. Для кожного пункту реєстру класифікувати будь-яку прогалину точно як одну з: `missing`
   (повністю відсутнє), `partial` (існує, але не повністю задовольняє), `contradicts` (код
   активно конфліктує з заявленим наміром чи MUST конституції), `unrequested` (код робить
   те, про що ніхто не просив — виноситься для обізнаності, ніколи не видаляється
   автоматично). Мало чи взагалі немає коду → розглядати весь обсяг як `missing`, а не
   провалюватись; нічого не бракує взагалі → нуль знахідок.
5. Серйозність: CRITICAL (порушення MUST конституції, чи missing/contradicts, що блокує
   історію P1) > HIGH (missing/partial на основній FR/критерії прийняття) > MEDIUM (partial
   на другорядній вимозі, чи необґрунтоване unrequested-додавання) > LOW (рівень полірування).
6. **Спочатку показати таблицю знахідок у чаті**, перед будь-яким записом — ID / тип
   прогалини / серйозність / source-ref / доказ / залишкова робота — плюс підсумкові метрики.
7. **Якщо є дієві знахідки**: дописати `## Phase N: Convergence` (N = найбільша існуюча фаза
   + 1) у `tasks.md`, по одному рядку
   `- [ ] T{next} <опис> per <source-ref> (<gap-type>)` на знахідку, спочатку CRITICAL/HIGH,
   ID продовжуються з поточного максимуму — ніколи не повторюються й не перенумеровуються.
   **Якщо немає жодних**: файл взагалі не torкатись; звітувати
   `✅ Converged — the implementation satisfies the spec, plan, and tasks.`
8. Рекомендація наступного кроку: `tasks_appended` → знову запустити `/speckit-implement`
   (наступний запуск converge повинен знайти суворо менше пунктів); `converged` → переходити
   до рев'ю/PR, подальший прохід implement для заявленого обсягу цієї фічі не потрібен.

## 9. `speckit-taskstoissues`

**Одним рядком**: Перетворити існуючі задачі на дієві, впорядковані за залежностями GitHub
Issues для фічі на основі наявних проєктних артефактів.

**Коли**: Опційно, має сенс лише якщо git-рімоут репозиторію — справді GitHub.

**Алгоритм**:
1. `check-prerequisites.sh --json --require-tasks --include-tasks` → шлях до `tasks.md`.
2. `git config --get remote.origin.url` — **жорстка ворітниця**: продовжувати лише якщо це
   резолвиться у URL GitHub; скіл явно попереджає, що за жодних обставин не можна створювати
   issues у репозиторії, що не відповідає рімоуту.
3. **Дедуплікація перед створенням будь-чого**: зібрати кожен ID задачі (шаблон `T\d{3}`) з
   `tasks.md`, потім пройти по існуючих issues репозиторію через `list_issues` GitHub
   MCP-сервера (без фільтра `state`, щоб перевірялись і відкриті, і закриті; `perPage: 100`,
   пагінація через курсор `after`/`endCursor`), зіставляючи кожен заголовок issue з
   `\bT\d{3}\b` (з межами слова, щоб `ST001`/`T0010` не збіглись хибно), щоб позначити, які
   ID задач уже мають issue. Зупинити пагінацію, щойно всі ID задач враховані, або сторінки
   закінчились — це обмежує кількість API-викликів навіть у репозиторіях із великою історією
   issues.
4. Для кожної задачі, яка **ще не** покрита: прибрати початковий `- [ ]` і будь-які маркери
   `[P]`/`[US#]`, щоб отримати `<ID>` і `<опис>`, створити GitHub issue з заголовком
   `T001: <опис>` (ID один раз, далі опис). Пропустити (і звітувати) будь-яку задачу, чий ID
   уже був зіставлений на кроці 3.

**Це єдиний скіл, що торкається зовнішньої, спільної системи (GitHub Issues)** — ставитись до
нього з такою ж обережністю, як до будь-якої іншої дії зі справжнім, важко оборотним,
видимим-для-інших радіусом впливу.

## Спільна обгортка (кожен скіл, не повторюється вище)

- **User Input**: сирий текст `$ARGUMENTS`, який користувач набрав після slash-команди —
  завжди враховується, якщо непорожній.
- **Pre-Execution Checks**: шукати `.specify/extensions.yml`; для релевантного ключа `before_*`
  пропускати вимкнені хуки, не оцінювати вирази `condition` (це залишено зовнішньому
  `HookExecutor`), виводити обов'язкові хуки як блок `EXECUTE_COMMAND:`, який має бути реально
  викликаний і дочекатись результату, виводити опційні хуки лише як пропозицію. Мовчки
  пропустити все це, якщо файл відсутній чи не має релевантних записів.
- **Mandatory/Post-Execution Hooks**: ідентичний механізм для ключа `after_*`, виконується
  прямо перед власним Completion Report скілу.
- **Примітка про екранування одинарних лапок**: кожен скіл, що звертається до shell,
  нагадує собі екранувати аргументи типу `I'm Groot` як `'I'\''m Groot'` (або віддавати
  перевагу подвійним лапкам) при побудові рядків shell-команд.
